# Diagnose duplicate profile credentials before cleanup

The [schema-preserving cleanup utility](Profile-Credential-Cleanup.md) is now available.
Start with the read-only pilot below, then follow that guide for selected item removal.

Run this read-only pilot for one affected user before deleting data. The script
compares the known user item in the production and Beta connections with the
shared Profile API certifications and awards. It never changes the schema,
connection, application, source precedence, or user profile.

## Why a single profile can contain repeated credentials

The current samples configure two sources: `mslearncred` (2.3) and
`mslearncredbeta` (2.4 Beta). Both sync scripts generate an externalItem ID
from the configured prefix (default `u`) and the Entra object ID with
nonalphanumeric characters removed. Item identity is scoped to its connection:
the same item ID in two connections is two separate source records.

This makes overlapping source data a plausible explanation, not a confirmed
diagnosis. The configured operational JSON files, CSV mappings, external items,
Profile API output, and UI must be compared. Source precedence does not, by
itself, prove that identical collection members will be deduplicated.

The sync flags `RemoveStaleManaged` and `PreserveUnmanaged` act on the item
being synchronized. They do not clean up another connection's user item.

In 2.4, an Applied Skill is intentionally represented in a custom search
property and in the awards property. Those are two representations for different
purposes, not two visible awards by definition. Credly badges are included in
the certifications collection by the current sync implementation.

## One-user pilot

1. Pause automatic runs of both synchronization versions for the pilot user.
2. Copy `99-Test-MSLearnProfileDuplicates.ps1` from Support to the operational
   project root, alongside the scripts and the Config and Data directories.
3. Open PowerShell 7 in that project root and run:

```powershell
& '.\99-Test-MSLearnProfileDuplicates.ps1' -UserPrincipalName 'user@contoso.com'
```

For different paths:

```powershell
& '.\99-Test-MSLearnProfileDuplicates.ps1' `
    -UserPrincipalName 'user@contoso.com' `
    -ProjectRoot 'C:\SandBox\MSProfileCard' `
    -ConfigPaths @(
        'Config\MSLearnPeopleConnector.json',
        'Config\MSLearnPeopleConnector.beta.json'
    )
```

Both files must be operational configurations with valid existing application
credentials. Each CSV must have exactly one enabled row for the selected user,
and both rows must target the same Entra object ID and tenant. The script uses
the existing Microsoft.Graph.Authentication module and connector application
permissions for item reads. A separate delegated sign-in requests
`User.Read.All` for Profile API reads; tenant admin consent may be necessary.
OAuth token requests use POST; all Graph data requests use GET.

The script exports timestamped JSON evidence and a CSV comparison to Reports.
The raw JSON retains full external items and Profile API records, including
any source metadata returned. It does not export configurations, secrets or
tokens. Reports contain personal information: keep them local and share only
the relevant, redacted evidence. Do not commit operational reports to GitHub.

## Interpret the evidence

| Observation | Interpretation / next check |
| --- | --- |
| Same credential exists once in each connection and twice in the profile | Overlapping sources are a strong candidate; verify source metadata or the profile-card export. |
| Credential is repeated inside one externalItem collection | Inspect source parsing and merge keys before cleanup. |
| Each source item is unique but profile repeats remain | Inspect source metadata, historical writes and profile propagation. |
| Profile API has one record but the UI shows two | Compare applications and refreshed sessions; UI/cache propagation is a candidate. |
| Similar names have different credential IDs or issuance dates | These may be distinct credentials or renewals; do not treat name matches as proof. |
| Read returns an error, including 403 or 404 | Review the failure, mapping and permissions; an unsuccessful read does not prove absence. |

Match candidates use certification ID when present, otherwise a normalized
display name. These are investigation groups, not deletion targets. Full dates,
record IDs, descriptions, URLs, source and modification metadata are retained
in JSON. The Profile API may not expose a connector ID in its source field;
do not infer ownership from the display name or generic source type. If needed,
export profile-card data to identify source IDs.

Scope: the pilot reads the deterministic item ID generated by each current
configuration. It does not enumerate every item or discover historical IDs from
earlier prefixes or manual writes. Include any known historical configurations
explicitly and investigate older IDs separately if the evidence calls for it.

## Cleanup design after the pilot

The desired maintenance script should preview selected users and explicitly
selected connections, back up their items, support `-WhatIf`, and delete only
verified user externalItems through:

```text
DELETE /v1.0/external/connections/{connectionId}/items/{externalItemId}
```

It should leave schemas, connection registrations, service principals and
precedence settings intact, and record individual results and failures. Removing
an entire externalItem also removes its custom search properties; it does not
touch the user's Entra account or mailbox.

Do not implement a blind deletion of all certifications and awards in the
shared profile. That could affect other sources or manually added records.
Do not assume deleting an externalItem guarantees immediate removal of every
materialized profile facet; verify the pilot after propagation. If materialized
records remain, determine their source and supported deletion path before
extending the cleanup.

After a pilot cleanup, keep synchronization paused for **at least 12 hours**
as an operational waiting period, then recheck Graph and the profile card.
This is not a Microsoft SLA or a guarantee of complete removal. Microsoft
documents up to six hours for initial connector availability and possible
delays for removal; it does not establish a universal 12-hour deletion deadline
in the references below. If duplicates remain, continue diagnosis rather than
resynchronizing automatically.

Once removal is verified, synchronize only the intended 2.4 source for the
pilot user, using the existing sync script's supported user selection. Validate
the final profile before expanding cleanup to the remaining users. Running both
versions again against the same users can recreate overlapping source data.
